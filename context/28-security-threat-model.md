# Security threat model and release evidence

Status: proposed design, researched 2026-11-15. This is not an audit, implemented protection, or ASVS certification. It extends documents 08, 12, 13 and 43; task numbers refer to [the implementation plan](15-implementation-plan.md). All verification cases below remain pending. FreeGG endpoint behavior is user-reported and unverified; no provider request was made for this research.

## Assets, actors and boundaries

The highest-value assets are Google-linked identities, sessions, saved birth/profile revisions, private questions/readings, exports, encryption keys and provider credentials. Corpus integrity also matters: edition rights, exact excerpts, passage hashes, reviewed rules and published generations determine whether an apparently authoritative answer is legitimate. Availability includes the finite generation budget and the ability to complete deletion while the web host sleeps.

Consider an anonymous attacker, a malicious signed-in user, a compromised administrator, a hostile PDF supplier, an injected passage author, an external provider and an operator making a configuration mistake. A legitimate administrator can accidentally import adversarial bytes; administrator-only import does not make parsing safe. Google authenticates an identity; it does not grant application administrator privileges.

The browser crosses an authentication boundary into FastAPI. FastAPI crosses separate boundaries into PostgreSQL, Qdrant, object storage and the external model provider. The offline ingestion parser crosses from untrusted files into worker privileges. The answering workflow crosses from evidence data into model output, then into HTML. PostgreSQL remains the proposed authority for ownership, rights and publication; vectors and caches cannot grant access. These are project design decisions, not vendor security guarantees.

Use ASVS 5.0.0 as the proposed verification baseline, with applicable Level 2 requirements selected and versioned during Task 9. The inspected ASVS site identifies that release and provides a verification framework [S2]. No requirement numbers or compliance claims are invented here.

## Critical design responses

**Login transactions.** Store state, nonce and PKCE verifier server-side for ten minutes, tied to an opaque browser-binding cookie. Consume state atomically; failures require a fresh login. State binds the browser request, nonce binds the token, and PKCE binds code redemption; none substitutes for token validation. Test S256 compatibility before enabling production; do not silently downgrade. Validate allowed signing algorithms and issuer keys through the maintained library, reject stale JWTs, and scope audience to this deployment's client. Normalize only Google's documented issuer forms; identity remains issuer plus subject, never email [S1]. Application requests use opaque sessions rather than accepting old Google JWTs as application bearer tokens.

**XSS and CSRF response.** Treat a successful XSS finding as possible authenticated-action compromise despite HttpOnly cookies. Disable the affected renderer, suppress poisoned saved content, revoke exposed sessions where warranted, and assess outbound disclosures using metadata-only audit events. Fix the shared rendering path and replay fixtures across full pages, HTMX and export. A CSRF finding blocks affected writes until token/origin checks cover every route; callback state remains a separate login defense [S3, S4, S7]. Proposed CSP should allow only the application's required assets, exclude arbitrary remote images, restrict connections/forms and deny framing; verify the chosen HTMX configuration actually works under that policy.

**Role or ingestion compromise.** Revoke administrative sessions and credentials, freeze publication, quarantine suspect artifacts and compare published hashes with reviewed manifests. Parsing runs as an unprivileged isolated process without database/provider credentials; an orchestrator grants only the input/output paths needed. The privacy executor should not inherit parser risk merely because both use the same application package. Job kind, owner scope and referenced object must be validated server-side. An administrator's supplied path or command is never executable configuration [S8].

**Injection and withdrawal.** Prompt delimiters are useful but not a security boundary. The service must prevent access to secrets even when the model follows hostile instructions. Citation IDs resolve through server-owned mappings; raw model URLs and remote images are rejected [S5]. Recheck ownership and rights before persistence and again before serving. Withdrawal denies newly requested content immediately, invalidates caches and queued exports, then removes index entries asynchronously. Already downloaded exports cannot be recalled; explain that limit rather than claiming deletion from recipients' devices. Preserve non-serving audit references to explain why a historical citation is unavailable.

## Launch blockers and accountable handoff

Identity owner must close threats 1, 3–6 and 17 through Task 2 evidence. Corpus/retrieval owners must prove quarantine, publication integrity and withdrawal through Tasks 4–6. Answer/provider owner must prove payload minimization, bounded spending and injection containment through Tasks 1/7. UI/privacy owner must prove renderer, fragments, exports, caches and deletion through Task 8. Operator owns network isolation, key rotation, production settings and restore evidence through Task 9.

Before real-user launch, attach reproducible test results, redacted configuration review and named signoff to each applicable threat. Resolve provider processing/retention terms and reliable privacy execution first; otherwise retain synthetic-only operation. No P0 remains open, and no P1 capability is exposed without its control evidence. The launch reviewer records residual risks and applicable ASVS coverage; documentation completion is not security verification.
